# 보이스타로 프론트엔드 초기 세팅 제안서

> **문서 상태:** 검토용 제안서
>
> **대상 플랫폼:** 모바일 웹 — Safari, Chrome
>
> **기반 자료:** 내영 님의 음성 상담 PoC 및 백엔드 기술 스택·인프라 초안
>
> **진행 방식:** 내영 님에게 제안 내용 확인 후, Codex를 활용한 직접 세팅 또는 도움을 받아 진행
>
> **디자인 방식:** 미정 — 무드보드·Codex·Figma 활용 예정, 작업 순서 협의 필요

## 문서 목적

기존 PoC를 실제 서비스로 발전시키기 위한 프론트엔드 기술 구성, 개발 환경, 화면 구조 및 디자인 적용 방식 제안.

초기 범위는 화면 개발과 백엔드 연동을 위한 기반 마련. 실제 음성 연결·결제·이용권 차감은 담당자와 구현 방식 및 정책 확인 후 단계적으로 적용 예정.

## 1. 프론트엔드 기술 구성

백엔드의 Python·FastAPI 도입 검토를 고려한 별도 React 프론트엔드 구성 제안.

프론트엔드와 백엔드는 API를 통해 연결하는 구조로, 서로 다른 개발 언어 사용 가능.

| 항목 | 제안 기술 | 사용 목적 |
|---|---|---|
| UI 개발 | **React** | 재사용 가능한 컴포넌트 기반 화면 구성 |
| 개발 언어 | **TypeScript** | 데이터 형식 명시 및 코드 수정 시 오류 확인 |
| 개발·빌드 도구 | **Vite** | 로컬 개발 환경 및 배포용 빌드 구성 |
| 화면 이동 | **React Router** | 로그인·메인·상담·리포트 경로 관리 |
| 스타일링 | **Tailwind CSS + CSS 변수** | 화면 스타일 구현 및 공통 디자인 값 관리 |
| 기본 UI | **shadcn/ui** | 버튼·입력창·다이얼로그 등 기본 컴포넌트 구성 |
| 애니메이션 | **Motion** | 카드 등장·뒤집기·화면 전환 효과 구현 |
| 서버 데이터 관리 | **TanStack Query** | API 데이터 조회 및 로딩·실패 상태 관리 |
| 코드 정리 | **ESLint + Prettier** | 코드 검사 및 형식 통일 |
| 패키지 관리 | **npm** | 의존성 설치 및 실행 명령 관리 |

### 선정 방향

- Codex 중심의 개발과 팀원의 코드 검토·수정을 고려한 구성
- Tailwind CSS를 통한 스타일 작성 및 필요한 경우 별도 CSS 추가
- shadcn/ui를 기본 UI의 출발점으로 활용하고 서비스 디자인에 맞게 수정
- 타로 카드·리더 프로필·통화 화면은 서비스 콘셉트에 맞춘 별도 제작
- Motion은 실제 애니메이션 작업 시작 시 도입 가능
- 상담 화면 내부 상태는 React 기본 기능으로 우선 관리
- 별도 전역 상태 관리 도구는 필요성 확인 후 검토

## 2. 기존 PoC 활용 및 프로젝트 구조

기존 PoC에서 검증한 음성 연결과 상담 흐름을 참고한 React 화면 구성.

재사용 가능한 기능 로직과 새로 작성할 화면 코드의 구분 필요.

| 구분 | 활용 방향 |
|---|---|
| 음성 연결 | 연결·종료·마이크 제어 로직 확인 후 React 구조에 맞게 분리 |
| 카드 선택 | 카드 데이터 및 선택 규칙의 재사용 여부 검토 |
| 상담 흐름 | 연결·카드 선택·해석·상담 종료 단계 참고 |
| 화면 코드 | React 컴포넌트 기반으로 구성 |
| 이용권·결제·기록 | PoC의 데모 처리와 실제 백엔드 연동 구분 |

### 프로젝트 내부 구조 제안

```text
src/
├── app/          # 앱 시작 설정과 화면 경로
├── pages/        # 로그인, 메인, 상담, 리포트 등
├── components/   # 공통 버튼, 입력창, 레이아웃 등
├── features/     # 음성 연결, 카드 선택 등 기능별 코드
├── api/          # 백엔드 요청과 데이터 형식
├── mocks/        # 화면 개발용 임시 데이터
├── assets/       # 이미지, 아이콘, 폰트
└── styles/       # 공통 스타일과 디자인 값
```

### 구성 원칙

- 실제 코드가 필요한 시점에 해당 폴더 추가
- 저장소 내 프론트엔드 위치 및 작업 브랜치는 내영 님과 확인 후 결정
- 기존 PoC를 비교·실행할 수 있는 상태로 유지
- 음성 연결 코드와 화면 표시 코드의 분리를 통한 수정 범위 최소화

## 4. 프론트엔드와 백엔드 연결 및 환경 설정

프론트엔드는 화면과 사용자 조작, 백엔드는 인증·결제 검증·이용권 관리·상담 기록 저장을 담당하는 구조 제안.

프론트엔드가 백엔드의 비밀 정보를 가져오는 방식이 아닌, **필요한 작업을 API로 요청하고 결과를 받는 방식** 적용.

### 역할 구분

| 기능 | 프론트엔드 역할 | 백엔드 역할 |
|---|---|---|
| 사용자 정보 | 닉네임 및 프로필 표시 | 로그인 사용자 확인 및 정보 저장·조회 |
| 이용권 | 잔액 및 이용 가능 여부 표시 | 이용권 지급·사용·잔액 관리 |
| 결제 | 결제창 호출 및 진행 상태 표시 | 결제 금액·승인 결과 검증 및 이용권 지급 |
| 음성 상담 | 마이크 조작, 음성 연결, 통화 상태 표시 | 이용 권한 확인 및 연결 인증 준비 |
| 카드 | 선택·공개 효과 및 카드 내용 표시 | 카드 데이터 제공 및 선택 결과 기록 |
| 리포트 | 생성 중 상태 및 결과 표시 | 리포트 생성·저장·조회 |

### 이용권 조회 예시

> 프론트엔드에서 조회 요청 → 백엔드에서 로그인 확인 및 DB 조회 → 이용권 개수 응답 → 프론트엔드 화면 표시

### 비밀 정보 관리

백엔드에서 관리할 정보:

- OpenAI 정식 API 키
- PG사의 비밀 키
- DB 접속 비밀번호 등 서버용 접속 정보

프론트엔드에서 사용할 수 있는 설정:

- 백엔드 API 주소
- PG사가 공개용으로 지정한 클라이언트 키 등

프론트엔드의 `.env`에 작성한 값도 브라우저 코드에 포함될 경우 확인 가능하므로, 비밀 정보 보관 용도로 사용 금지.

### 음성 연결 방식

브라우저와 OpenAI 간 직접 음성 연결 방식 채택 시, 다음 흐름 검토.

> 프론트엔드에서 연결 준비 요청 → 백엔드에서 정식 API 키로 임시 인증 정보 발급 → 프론트엔드에 전달 → 음성 연결

정식 API 키는 백엔드에서 보관하고, 프론트엔드는 연결에 필요한 임시 인증 정보만 사용.

임시 인증 정보의 만료와 서비스 이용 시간 제한은 별도 관리 필요. 실제 연결 방식, 이용 시간 측정 및 종료 제어는 내영 님·백엔드 담당자와 협의 예정.

### 초기 세팅 범위

- 백엔드 API 주소 설정
- 필요한 설정 항목을 안내하는 `.env.example` 작성
- API 요청을 공통으로 처리하는 코드 구성
- 로딩·오류·로그인 만료 상태 처리
- 백엔드 구현 전 화면 개발에 사용할 임시 데이터 준비

### 백엔드 담당자와 확인할 사항

- 로그인 정보를 전달하는 방법
- 개발·배포 환경의 API 연결 방식
- API 요청·응답 데이터 형식
- 음성 연결 준비 및 상담 종료 처리 방식

## 5. 화면 경로 및 상담 진입 흐름

로그인부터 상담 종료 후 리포트 확인까지의 화면 구조 마련.

아래 경로는 초기 제안으로, 기능 범위와 구현 방식에 따라 조정 가능.

| 화면 | 경로 예시 | 주요 역할 |
|---|---|---|
| 로그인 | `/login` | 소셜 로그인 진입 |
| 닉네임 설정 | `/onboarding` | 닉네임 입력 및 저장 |
| 메인 | `/` | 타로 리더 소개, 이용권 확인, 전화 걸기 |
| 상담 | `/sessions/:id` | 특정 상담의 음성 연결 및 카드 표시 |
| 리포트 | `/sessions/:id/report` | 상담 요약 및 선택 카드 확인 |
| 이용권 구매 | `/tickets` | 이용권 선택 및 결제 진입 |
| 결제 결과 | `/payments/result` | 서버에서 확인한 결제 결과 표시 |

`:id`는 각각의 상담을 구분하는 식별자.

### 새 상담 시작 흐름

> 전화 걸기 → 로그인·이용권 확인 → 상담 생성 → 상담 화면 이동 → 음성 연결

최초 ‘전화 걸기’ 동작 이후 자연스럽게 연결되는 흐름 구성.

마이크 권한 확인 순서, 이용 시간 측정 시작점 및 실제 이용권 차감 시점은 별도 협의 필요.

### 기존 상담 URL 접근 시 처리

상담 화면 새로고침 또는 재방문 시, 새 상담 생성에 앞서 **해당 상담의 기존 상태 확인**.

화면 진입마다 새 상담 생성 시 발생할 수 있는 기록 분리 및 이용권 중복 처리 방지 목적.

| 상담 상태 | 화면 처리 방향 |
|---|---|
| 진행 중 | 재연결 가능 여부 확인 및 안내 |
| 종료됨 | 리포트 화면 또는 종료 안내 표시 |
| 존재하지 않음·접근 권한 없음 | 접근 불가 안내 및 메인 이동 제공 |
| 상태 확인 실패 | 오류 안내 및 다시 시도 제공 |

기존 상담 기록과 실제 음성 연결 상태의 구분 필요. 새로고침 후 카드·대화 맥락·이용 시간을 이어가는 범위는 PoC 검증 및 정책 협의를 통해 결정 예정.

버튼 중복 클릭이나 요청 재전송에 따른 상담 중복 생성·이용권 중복 차감 방지는 백엔드 처리도 함께 마련할 필요.

### 모바일 UX 확인 항목

- 마이크 권한 요청 및 거부 안내
- 연결 중·듣는 중·응답 중 상태 구분
- 카드 번호 인식 오류 및 재선택 안내
- 음소거·통화 종료 버튼의 명확한 표시
- 네트워크 끊김 및 재연결 안내
- 이용권 부족 및 이용 시간 종료 안내
- 리포트 생성 중·실패 상태 처리
- 모바일 하단 안전 영역 및 화면 높이 대응
- 키보드가 열린 상태의 화면 배치 확인

무료 체험 여부, 다음 이용권 사용 방식 및 비정상 종료 시 차감 기준은 정책 확정 후 반영 예정.

## 6. 디자인 적용 방식 및 공통 UI 준비

디자인 도구와 작업 순서는 미정.

무드보드와 레퍼런스로 서비스 분위기를 정리한 뒤, Codex와 Figma를 상황에 맞게 활용하는 방향 제안.

| 작업 방식 | 흐름 |
|---|---|
| Codex로 화면부터 구체화 | 무드보드 → Codex 화면 구현 → Figma 검토·수정 → 코드 반영 |
| Figma에서 먼저 구체화 | 무드보드 → Figma 시안 → Codex 구현 → 실제 화면 검토 |

Figma와 코드 간 자동 동기화를 전제로 하지 않는 작업 방식. 변경 발생 시 반영 기준이 되는 시안 및 구현 화면 확인 필요.

### 초기 디자인 기준

| 항목 | 정리할 내용 |
|---|---|
| 색상 | 배경·본문·강조·오류 등의 공통 색상 |
| 글꼴 | 제목·본문·버튼의 글꼴 및 크기 |
| 간격 | 화면 여백 및 요소 사이 간격 |
| 형태 | 버튼·카드·입력창의 모서리, 테두리, 그림자 |
| 이미지 | 리더 프로필 및 타로 카드의 시각 방향 |
| 움직임 | 카드 공개·화면 전환·음성 반응 효과 |
| 상태 표현 | 로딩·오류·비활성·연결 끊김 표시 방식 |

‘퀸의 마인드’ 콘셉트를 고려한 시각 방향 검토. 구체적인 색상·폰트·장식은 디자인 논의를 통해 결정 예정.

공통 디자인 값은 CSS 변수로 관리하여 여러 화면의 일관된 수정이 가능한 구조 마련.

### 컴포넌트 적용 방향

- 버튼·입력창·확인창 등은 shadcn/ui 기반으로 조정
- 타로 카드·리더 프로필·통화 화면은 서비스에 맞춰 별도 구성
- 카드 공개 및 화면 전환에 필요 시 Motion 적용
- 애니메이션 구현 시 모바일 성능 및 동작 줄이기 설정 고려
- 통화 상태는 시각 효과와 텍스트를 함께 사용하여 표시

최종 시안 확정 전에는 수정하기 쉬운 기본 화면 준비. 디자인 방향 결정 후 공통 스타일과 컴포넌트에 반영 예정.

## 검토 및 실행 절차

1. **내영 님 검토:** 기술 구성 및 PoC 재사용 범위 확인
2. **백엔드 협의:** API 연결·인증·상담 생성 및 종료 방식 정리
3. **초기 세팅 진행:** 확인된 범위부터 Codex를 활용한 직접 작업 및 필요 시 내영 님의 도움 요청
4. **결과 확인 및 공유:** 기본 실행·화면 이동·검사·빌드 확인 후 팀 공유

**초기 세팅 목표:** 모바일 웹 화면 개발, 디자인 수정 및 백엔드 연동을 이어갈 수 있는 공통 기반 마련.
